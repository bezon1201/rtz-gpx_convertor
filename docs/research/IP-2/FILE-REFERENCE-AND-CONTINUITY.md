# IP-2A — FileReference and Source Continuity Qualification

**Current handoff:** R11 freezes the minimum file-reference/security policy for final review; **B04 remains PARTIAL / OPEN; IP-2A remains PARTIAL / INCOMPLETE.** This does not qualify production transport, alias/provider behavior or preview/export continuity, and does not close B04. See [`IP-2A-R11-FILE-REFERENCE-POLICY.md`](IP-2A-R11-FILE-REFERENCE-POLICY.md) for current policy and B04 closure matrix. R4–R8 findings below remain historical evidence snapshots.

## Current IP-2A R11 minimum policy status

The conceptual `AuthorizedFileReference` is not a production type: paths are locators only; successful unsandboxed open is not a system grant; authorization, object identity and content continuity are separate. The minimum policy requires qualified authority/reacquisition, one secure target open, descriptor validation, bounded reads from that descriptor, no unsafe reopen, balanced scope lifetime if used, and fail-closed handling. Explicit bounded alias/symlink resolution may be supported only after qualification; no blanket rejection is imposed. At export, reacquire, reread, revalidate and compare a deterministic output-affecting semantic projection. Mismatch or inconclusive comparison invalidates route confirmation and dependent publication consent. No source digest by default.

Policy is frozen for final Architect review. Product transport, alias/symlink UX, provider/OS matrix and actual semantic continuity remain unqualified downstream work. B04 remains **PARTIAL / OPEN**; R11 ran no probe and authorizes no implementation.

## Historical R4 status summary

- **VERIFIED (this host, synthetic local files):** descriptor-backed reads remain bound to the opened filesystem object across rename/move, replacement of the old path, symlink retargeting and deletion. Path reopen can select a different object. Same-object in-place writes are visible on reread through the descriptor. POSIX type and read-permission checks worked for the tested directory, FIFO and mode-000 file.
- **VERIFIED (this host, Foundation API behavior only):** a plain bookmark followed a rename, was marked stale, and resolved to the moved file; resolving after deletion failed. Foundation resource/file identifiers were available and equal across the tested rename; generation metadata was available. These observations do not establish identity or content guarantees on another volume/provider/OS.
- **CONDITIONAL:** Apple documents Powerbox access from an Open/Save panel or Dock drop, security-scoped URL/bookmark lifecycle, and implicit scoped bookmark transfer to a receiving process. These documented mechanisms are candidates, not evidence that the planned Finder/Shortcuts workflow supplies or safely transports such a capability.
- **BLOCKED / NOT QUALIFIED:** the concrete Finder Quick Action / Shortcuts file carrier, sandboxed app and helper scope lifecycle, reusable export-time authorization, alias handling, File Provider behavior, and exact preview/export semantic comparison remain untested. **IP1-B04 remains PARTIAL / OPEN.**
- **REQUIRES EXTERNAL / CROSS-STAGE CONFIRMATION:** IP-2A, IP-5 and IP-7 must jointly settle reference transport, aliases, symlinks, security scope, permissions, and reacquisition rules; the product owner/Architect must review any final policy. No G3 decision is changed.

It compiles with the host Swift toolchain to a temporary binary, uses only small synthetic text files in a newly created local temporary directory, and cleans up. The case-level results cover normal open/read, rename and same-volume move, Foundation resource/file/generation identifiers, path replacement, in-place same-object mutation, symlink retargeting and `O_NOFOLLOW`, directory/FIFO classification, permission denial, deleted source with an open descriptor, plain bookmark rename/staleness/deletion, security-scope API calls in an unsandboxed process, and preview-versus-reacquired byte mismatch. Apple notes that a successful `startAccessingSecurityScopedResource()` must be balanced by `stopAccessingSecurityScopedResource()`, and unbalanced access leaks kernel resources. R4 calls returned `true` for both ordinary and bookmark-derived URLs in this unsandboxed command-line process. **That observation proves no sandbox grant**; it only verifies that this host accepted the API calls. See [Apple lifecycle guidance](https://developer.apple.com/documentation/foundation/url/startaccessingsecurityscopedresource%28%29?changes=l_10).

Apple documents `NSFileCoordinator` as coordination among file presenters and recommends using a coordinator per file operation. It can help produce coherent access for coordinated providers, but does not replace a capability, descriptor identity, bounded read, or semantic comparison. R4 did not test it. File Provider hydration, offline placeholder failure and provider replacement remain unqualified. See [NSFileCoordinator](https://developer.apple.com/documentation/foundation/nsfilecoordinator?changes=latest_minor).

## Identity evidence classification

| Observation | R4 classification | Limitation |
|---|---|---|
| Open descriptor plus `fstat` device/inode | **Strong same-open-object evidence for the lifetime of that descriptor on the tested filesystem.** | Does not prove unchanged bytes; inode reuse after close, filesystem/provider differences, and cross-volume identity are outside this evidence. |
| Foundation `fileResourceIdentifier` / `fileIdentifier` | **Useful same-object hints.** Both were available and equal across one same-volume rename. | Apple documents filesystem-specific limits; do not persist as a cross-volume or reboot identity. Never a content proof. |
| `generationIdentifier` | **Potential change hint.** Available in the tested resource values. | Not guaranteed to exist or have the same behavior on all volumes/providers; no cross-mount/copy guarantee. |
| Size, modification/change timestamps | **Useful change hints only.** They changed during the tested in-place write and metadata changed on rename. | Timestamp granularity, filesystem semantics and deliberate restoration prevent a content proof. |
| Path/filename or bookmark-resolved URL | **Insufficient for identity or content proof.** | A path can be replaced; a bookmark may track a resource and become stale without proving its bytes/content. |
| Full-file digest | **Not used and not recommended by default.** | Private route digest is opt-in only after documented need, privacy review, and explicit approval; a digest would still not establish authorization. |
| Parsed material route semantics | **Required continuity comparison, not yet empirically defined or tested.** | Must be a deterministic qualified projection of the validated route, including ordered points/names, route name/default behavior, leg/geometry and other output-affecting data; no source hash substitute. |

Apple references: [`fileResourceIdentifierKey`](https://developer.apple.com/documentation/foundation/urlresourcekey/fileresourceidentifierkey?changes=lat__1_3), [`fileIdentifierKey`](https://developer.apple.com/documentation/foundation/urlresourcekey/fileidentifierkey?changes=_10%2C_10), and [`generationIdentifierKey`](https://developer.apple.com/documentation/foundation/urlresourcekey/generationidentifierkey?changes=_2). Their documented caveats remain part of the design; R4 does not upgrade them into universal identity guarantees.

## Historical R4 candidate continuity contract for cross-stage review

This is a **candidate contract**, not a selected product API:

1. Treat every input, including Finder/Shortcuts/CLI-originated values, as an opaque, untrusted local-file reference. A path is only a locator. Do not trust the sender, extension, URL string, bookmark bytes, or file metadata without successful resolution/access and validation.
2. Receive/reacquire authority through a qualified native selection or bookmark mechanism. Start any required security scope for the smallest necessary lifetime; balance every successful start on every success, error, cancellation and timeout path. A missing, stale, denied, expired, or non-resolvable reference fails with an actionable diagnostic; stale bookmark refresh requires a new qualified access/preview flow.
3. Resolve aliases or a selected symlink only through an explicit, bounded OS reference operation. Never recursively walk/reopen an arbitrary path chain. Then open the resolved target once using a no-follow/identity-aware strategy, `fstat` the descriptor, require a regular file, enforce a byte ceiling during descriptor-backed reads, and close exactly once. The probe shows O_NOFOLLOW as a useful final-path primitive but does not define safe selected-alias semantics.
4. At preview, record only ephemeral minimum state needed for this invocation: authorized reference handle/data, descriptor identity while open, and the fully validated material route projection needed to reproduce the confirmed output. Do not persist full path, bookmark or source digest by default; do not log capability data or identifiers.
5. At export, reacquire authorized access and securely open/read/validate again. Compare the deterministic output-affecting semantic projection with the confirmed preview, including the effective route name and selected transformation. If equal, continue to a separately confirmed output using that fresh model. If the source cannot be reacquired or the projection differs or comparison is inconclusive, invalidate route confirmation and publication consent bound to the prior output; require a new preview and affirmative confirmation.
6. Do not infer unchanged contents from device/inode, resource identifier, generation identifier, size or timestamps. Never reopen a path solely because it string-matches a previously selected path. No automatic route repair, selection or navigation decision is permitted.

For a single uninterrupted conversion, the simplest proven object binding is to read and validate from one already-authorized descriptor. The preview-to-export contract still requires a second authorized read if export occurs after user review or source/model reconstruction. The confirmation comparison is semantic; it is not authorization and does not silently bind consent to another output.

## Finder / Shortcuts / helper process boundary

- Prior IP-1D evidence is retained: Shortcuts “as arguments” yielded zero arguments in its tested Text-action setup; stdin forwarding was exact for synthetic bytes; Finder Quick Action invoked but its actual file input/reference was unobservable. Do not generalize these results beyond that setup.
- This host’s `shortcuts help run` shows `--input-path <input-path>` but not an object/capability type. It proves only a CLI path option exists.
- Apple documents that a non-security-scoped bookmark made from a security-scoped URL can carry its implicit scope when passed to a receiving process, whose sandbox automatically attempts to extend when resolving/using it. Apple also documents passing bookmark data to a helper process. That generic platform capability is not proof that a specific Finder Quick Action or Shortcut can produce, preserve, and safely deliver it to the chosen local CLI.
- A path-only Shortcut transport must remain an untrusted locator and must fail if the receiving component lacks independently granted access. Never treat Shortcuts' successful invocation as user-selected file authority.
- IP-5 owns transport serialization and safe helper discovery; IP-7 owns native picker/Finder input and user-flow evidence; IP-2 owns descriptor-backed bounded read and parser boundary. Test the real signed/sandboxed target and candidate OS matrix before freezing transport.
